## Proposed bounded ownership and interfaces

Names in this section are prospective APIs, not existing callable APIs or committed types. The implementation should keep the proposed responsibilities even if repository naming conventions change.

A modern `CliCompileContinuation.RunAsync` dispatches using the already-effective B3OptionBag selector. The default/explicit Boogie branch calls the old synchronous Run unchanged. Only modern B3 build/run/test and the source dependency build continuation use the neutral branch. The legacy driver's B3 capability rejection remains. Translate, audit, counterexample/metric-dependent commands and unrelated command routes are not silently admitted.

An engine-free `PreparedCliInputs` owns an immutable collection of admitted DafnyFiles (including their per-file options and trust/compile dispositions), foreign target filenames, ordering/program naming, project and effective options for one compilation epoch. Reuse the existing compiler resolution and GetDafnyFiles classification logic without constructing SynchronousCliCompilation. Freeze the collection once; retain foreign files and stdin. Selection must occur before parsing because parser/library handling and standard-library translation depend on the target backend. Library/source dependency preparation occurs once and returns a failed preparation disposition before parent continuation if it fails. Do not collect a project twice, append standard-library roots twice, collapse file-specific options into parent options, or reinterpret foreign target files as Dafny.

Add a constructor-owned optional prepared-root input seam to CliCompilation/Compilation. Existing calls use the exact original DetermineRootFiles branch. The new branch waits for Start and consumes the prepared list instead, preserving diagnostics/event bookkeeping. Do not assign the public RootFiles property after constructor tasks have started: ParseAsync can already await the original task. Parsing loads source content once into the Program; both verification and target generation consume that same resolved Program object. No verified receipt can authorize a second parse or compilation from reread text.

A reusable `VerifyCommand.VerifyAndReportAsync(CliCompilation)` or equivalent narrow continuation reuses the existing subscriptions and diagnostic ordering, summary/log capability gates, and lazy neutral work execution. The B3-only continuation reuses those consumers. Keep the existing options-based VerifyCommand.HandleVerification body and native event/subscription timing unchanged in this first checkpoint; do not refactor the Boogie/default handler to obtain this reuse. Do not call HandleVerification(options) as a separate pass. No B3 branch calls BoogieAsync, engine.GetVerificationTasks, DafnyMain.BoogieOnce, passification or a Boogie prover. Preserve translation mutex and large-stack execution, current source-to-generated-unit owners and all generated checking units admitted by existing policy.

Cli-owned selected backend lifetime must be explicit. Cancellation before or during resolution/preparation/verification prevents compilation. Dispose/cancel the owned compilation and B3 backend in finally; close its result subscriptions. Do not change ProjectManager-owned backend lifetime, native checker pooling/publication timing or default pipeline cleanup. Target code generation uses the existing large-stack tail after completed B3 cleanup. This does not assert new process containment or full target-tool cancellation capability.

## Complete-result, empty-scope and compiler relation

Define an internally constructed `CliVerificationReceipt` bound to one owned compilation epoch, exact effective backend/configuration, resolved Program reference and requested verification scope. The receipt cannot be manufactured from options.Verify, DidVerification, a zero diagnostic count or an empty result list. A caller-supplied bool named verified must not replace this relation.

For verification enabled, freeze the finite current scope before work: source/module/symbol eligibility under the existing resolver/translator ShouldVerify rules, admitted dependencies and existing excluded declarations. Retain the reasons for trust-policy/existing-attribute exclusions. Include the pre-VC generated checking-unit inventory returned by successful preparation, with exact neutral source owners and unit keys. Each admitted unit must belong to the requested current scope, appear once, and have one accepted terminal record. A prepared unit assigned to an otherwise missing owner cannot disappear through grouping. Position/symbol filters are not added to build/run/test; a constrained verification scope cannot authorize ordinary compiled output as fully checked.

Preparation admission must not be reconstructed solely from the number of CanVerifyResult values yielded by VerifyAllLazily. Its DidVerification flag is set before translation and a failure can happen before CanVerifyPartsIdentified. The new B3 compiler continuation owns an awaited module-preparation ledger: each expected module has NotStarted, Preparing, Completed or Failed, and only Completed carries the actual complete prepared work-item inventory. Capture that inventory at successful module preparation, before per-owner PartsIdentified or filtering, using a narrow B3-continuation preparation receipt seam. Exceptions/cancellation and TranslationHasErrors set Failed even if no part event or lazy yield follows. Await all expected preparations rather than relying on fire-and-forget scheduling or an empty result enumeration. Missing/omitted, duplicate, unknown-owner and out-of-scope IDs are rejected against this inventory.

A null ResolutionResult, resolution.HasErrors or resolution.CanVerifies==null is Rejected, not a legitimate empty proof scope. A nonnull empty eligibility dictionary can enter the independently justified CompleteEmpty relation below only after successful resolution and explicit scope admission; absence of a module-preparation record cannot be replaced by that empty dictionary. For every nonempty unit, both terminal result and normal observable completion are required on B3, retaining RequireCompletion. A terminal record followed by stream fault, truncation or cancellation cannot authorize the compiler. Cancellation is checked again at the continuation boundary, including cancellation after a terminal record. These checks are B3 compiler-receipt checks; preserve the native Boogie event timing and existing default route bytes.

The relation has four distinct dispositions:

* Disabled: ordinary --no-verify is explicit. No verification translation/preparation/tasks occur. Compilation may proceed after normal parse/resolve/compiler policy checks, but provenance says verification not attempted.
* CompleteNonempty: resolution and all requested module preparations succeeded without reported translation errors; the expected nonempty inventory equals the completed inventory; every terminal result IsVerified; no cancellation, fatal diagnostic, capability error or exception remains. Compiler continuation is permitted.
* CompleteEmpty: the full current scope has independently justified zero obligations. Either successful shared translation/backend preparation returns zero eligible units, or resolution/source classification explicitly identifies no verification-eligible declarations/modules under existing policy. Record why, counts zero and no proofs/attempts; do not create a fake Verified task or claim any assertion was proved. Empty module/task collections without completed admission/preparation cannot produce this disposition. Missing dependencies, preparation failures, orphan owners or lost events are Rejected.
* Rejected: all other states, including Failed, Unknown, TimedOut, OutOfResource, OutOfMemory, Cancelled, Unsupported, ToolError, Bounded, incomplete apparent Verified, pending/exceptional streams, duplicate/out-of-scope/missing unit identity, failed admission/preparation, stale epoch or fatal diagnostics. Compiler/runtime continuation is forbidden and exit is nonzero.

The scope remains current-policy-relative. Existing `.doo` trusted inputs, explicit source-library exclusions and `{:verify false}` do not become B3 proofs. They must be labeled excluded/trusted when explaining the receipt. This receipt is an operational authorization relation, not a formal proof that the normalizer/worker implements Dafny semantics; separate semantic acceptance remains unchanged.

Collect module-local prepared/completed identities while that module is owned; seal a deterministic inventory digest/count and release it with existing caches. Global aggregate counts must be checked for overflow. Do not introduce unrelated solver/request/semantic caps or retain every expression AST again. The metadata relationship and completion checks are independent of console text. Numerical budgets and existing worker failure classifications stay as they are; if implementation needs an additional project-wide receipt allocation cap, propose it separately rather than borrowing unrelated request bounds.

Only after Disabled or one of the two complete dispositions may the modern B3 path call the existing static CompileDafnyProgram with the same resolved Program, prepared foreign filenames and original output/main/runtime options. Retain its post-verification hooks, target capability errors, compiler exception diagnostics and actual runtime result. A verification-enabled Rejected receipt must not invoke even OnPreCompile or spill an accepted target/library. Do not convert a target compiler/runtime error into verification success.

## Explicit skipped verification

Ordinary --no-verify sets the existing serialized NoVerify=true. Before CliCompilation.Start, set ShouldProcessSolverOptions=false; never call VerifyAllLazily, shared verification translation, backend PrepareAsync, WorkerPackage loading, SolverDigestAsync, or solver-version probing. Constructing a non-executing selected B3 backend is permitted but not required for this branch; the Boogie factory is forbidden. Parse/resolve and target compiler/runtime still execute when later authorized, so skip is not a bypass of language soundness/cardinality/type checks.

HiddenNoVerify remains an explicit B3 capability error. Do not silently turn it into ordinary skip or emit a verified-looking .doo. Preserve all Boogie handling byte-for-byte. For this first modern checkpoint, explicit no-verify combined with pre-VC/VC dumping has a capability disposition: reject rather than silently omit a requested dump or execute VC generation. A separately reviewed engine-free pre-VC dump path can be added later. Existing unsupported custom solver/Boogie/proof-analysis options retain honest dispositions; inactive options must be described as inactive because verification is intentionally disabled, never as implemented B3 capability.

## Dependency recursion and library child command

HandleDafnyProject must call the modern dispatcher for selected B3 dependency builds with copied effective options and the explicit LibraryBackend. It must keep current asLibrary/no-verify/dependency-trust decisions. No recursive dependency can fall back to Boogie merely because it is a library build. Failed dependencies do not provide an accepted DooPath to the parent. Keep existing Boogie recursion unchanged.

For LibraryBackend execution, add a B3-only child argument path in RunTargetDafnyProgram. Forward the explicit B3 selection and the finite currently supported execution configuration: packaged worker path, resolved explicit solver path, verification time/resource/core limits and supported arithmetic selector. Preserve main arguments and target cs. Forward effective ordinary --no-verify when the parent has it or the requested child verify argument is false. Do not serialize all internal options or translate arbitrary solver/Boogie strings into child flags. The Boogie argument path remains unchanged.

Enabled B3 child execution on a .doo still loads a trusted dependency with ShouldNotVerify=true. A child command must not claim B3 reverification of that artifact. Forwarding selection/config prevents silent fallback and preserves error handling, but does not change the old dependency trust contract. Missing B3 package/configuration with verification enabled remains a nonzero error even when a trusted input produces no current obligations, consistently with current enabled resolution validation.

## Provenance without a format or trust change

For the first checkpoint, leave existing .doo ManifestData serialization, version1.0, option registry scopes, validation and .dtr serialization unchanged. Ordinary --no-verify continues to be recorded by its existing global option and retains OptionLibraryImpliesLocalError. Do not register verification-backend as a new global compatibility requirement: that would reject compatible existing Boogie libraries under a selected B3 invocation.

Optional B3 informational provenance belongs in the explicit CLI compilation receipt and, if persisted with a generated library, an adjacent B3-only sidecar. It must not be incorporated into .doo/.dtr format1.0, used by DooFile.Validate, substitute for existing option checks or grant trust. A missing or stale informational sidecar cannot make an artifact verified. Boogie/default output creates no new sidecar and existing default bytes remain unchanged. The sidecar's source/library identity, current-scope disposition and dependency boundary must derive from the actual completed or Disabled receipt, not options.Verify. Emit no fabricated solver version; configuration's requested5.1 is not an observed version.

If a later design instead uses optional fields inside .doo, treat that as a separate design revision requiring pinned old/new-reader compatibility and default-byte evidence before coding. No such compatibility result is asserted here. This sidecar choice narrows the earlier prose suggestion of optional manifest fields to meet the explicit no-format/no-trust/default-byte boundary.

LibraryBackend must continue serializing AfterParsingClone to avoid resolved prefix-module collisions. Pass any informational receipt separately from the resolved Program to the library output context; do not annotate/replace the parsed source tree or infer proof status from that clone. TranslationRecord remains translation metadata, not a proof certificate. Unsupported/error verification never reaches the accepted library writer in the enabled branch.

## Command behavior and finite controls

B3 build/run/test with verification enabled prepare and finish the selected backend before target generation; nonverified outcomes are nonzero. Ordinary skipped verification proceeds without prover/worker lookup and reports not attempted. Hidden skip, legacy B3, translate B3 and unsupported analysis features retain explicit capability errors. CLI/project overrides choose exactly one backend; recursive source dependencies and library child commands use that choice/configuration. Boogie default and explicit Boogie continue through the old path unchanged.

The generated test runner retains its existing no-verify attribute; do not invent verification for try/recover or silently drop ordinary test method WF/body checks. Runtime tests can succeed or fail independently after their source verification; a runtime pass is not a new proof result.

## Structured admission diagnostic addendum

Source review found that the legacy file helper's separate standard-library reporter can emit a validation error and omit a requested file while returning its existing success exit value. It can also emit admission warnings before the neutral CLI has subscribed. The modern prepared-root continuation must retain those diagnostics; neither helper success nor an empty root list is proof of complete admission.

The B3-only caller supplies one structured batch reporter through an optional file-helper argument. When the argument is absent, every existing default/legacy reporter and helper behavior is retained. The new caller freezes source, source-library and standard-library admission diagnostics with its prepared input collection. Errors and warning-as-error are rejected before constructing the parent compilation. Allowed diagnostics are replayed once through the owned CLI diagnostic subscription before Start, so they participate in existing warning policy and console reporting. This adds no library trust rule, source reread, output-text parsing or successful empty-input heuristic.

Prospective controls include omitted standard-library admission, source-library errors, allowed admission warnings and rejected warnings. These are implementation controls, not a claim that the 67 planning rows form an executed test census.
